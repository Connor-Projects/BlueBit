### 1.2 CCC Configuration

- **Subscribed value:** `{0x01, 0x00}` (0x0100 = ENABLE_NOTIFICATION_VALUE)
- **Unsubscribed value:** `{0x00, 0x00}` (0x0000 = DISABLE_NOTIFICATION_VALUE)
- **Source:** `ClientPreferredConnectionModeCharacteristic.java` Companion object

### 1.3 MTU

- **APK default MTU:** 185 (`StackPeerKt.STACK_NODE_DEFAULT_MTU`)
- **Actual negotiated MTU:** 247 (Inspire 3 offers higher)

### 1.4 Gattlink Frame Format (from `GattlinkPacket.Companion.parse()`)

```
Byte 0:
  Bit 7 (0x80): isControl flag
  Bit 6 (0x40): hasAck flag
  Bits 0-4 (0x1F): Packet Sequence Number (PSN)

If hasAck=true and isControl=false:
  Byte 1 bits 0-4: Data PSN
```

**Decoded fields:**
- `size` = total packet length (including header)
- `isControl` = control packet vs data packet
- `hasAck` = carries acknowledgement
- `ackPsn` = acknowledged sequence number (if hasAck)
- `dataPsn` = data sequence number
- `firstByte` = raw first byte

### 1.5 Native Code Boundary

The frame **construction** (what bytes to write to ABBAFF01) is in the native GoldenGate C/C++ library:
- `TxSink.putData()` receives bytes from native layer
- `GattlinkPacket.Companion.parse()` decodes received bytes
- `RemoteGattlinkNodeDataSender` forwards native bytes via `GattCharacteristicWriter`

**The exact initialization sequence is NOT in Java source.** It is generated by the native `golden-gate` shared library.

## 2. Experimental Setup

### 2.1 Method

1. Connect to Inspire 3 via BLE
2. Request MTU = 185
3. Discover services
4. Locate Gattlink service (ABBAFF00)
5. Verify ReceiveCharacteristic (ABBAFF01) and TransmitCharacteristic (ABBAFF02)
6. Write CCC descriptor on ABBAFF02: `{0x01, 0x00}`
7. **Listen for 30 seconds** (receive-only — no TX frames sent)
8. Disconnect

### 2.2 Why Receive-Only?

Per instructions: *"Do NOT invent Gattlink framing bytes. Every byte sent to the Inspire 3 must be justified by a concrete APK/source reference."*

The initialization frames are generated in native code. Without reverse-engineering the `.so` file, we cannot safely construct the startup sequence.

## 4. Analysis

### 4.1 Why No Notifications?

The Inspire 3 Gattlink transport is **half-duplex at initialization**: the tracker waits for the phone to send Gattlink startup frames on ABBAFF01 before it responds on ABBAFF02.

This matches the APK architecture:
- `RemoteGattlinkNodeDataSender` writes to ABBAFF01 (client → tracker)
- `RemoteGattlinkNodeDataReceiver` listens on ABBAFF02 (tracker → client)
- The native layer drives the protocol state machine

### 4.2 What Would Be Needed to Proceed?

1. **Reverse-engineer the native `.so`** — extract the exact initialization bytes from `libgoldengate.so` or similar
2. **Capture Fitbit APK traffic** — use a BLE sniffer during genuine Fitbit app pairing to observe the initialization handshake
3. **Analyze the native protocol** — the Gattlink layer sits below DTLS/CoAP; understanding the native initialization requires ARM disassembly

## 5. Frame Decoder Implementation

The decoder in `FitbitGattlinkDiagnostic.kt` correctly implements the APK `GattlinkPacket.Companion.parse()` logic:

```kotlin
val firstByte = value[0].toInt() and 0xFF
val isControl = (firstByte and 0x80) != 0
val hasAck = (firstByte and 0x40) != 0
val psn = firstByte and 0x1F

val ackPsn: Int? = if (hasAck) psn else null
val dataPsn: Int? = when {
    isControl -> null
    !hasAck -> psn
    value.size > 1 -> value[1].toInt() and 0x1F
    else -> null
}
```

This decoder is ready for use when RX frames become available.
