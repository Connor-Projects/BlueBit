## 1. Objective

Trace the official Fitbit app's preconditions for invoking `PUT bond/control`, to separate hypothesis **C** (resource-specific authorization) from hypothesis **D** (required sequencing/pairing state) for why the Inspire 3 returns `4.01` to BlueBit.

---

## 2. Headline result

The official app can authenticate to the tracker with a **MobileData PSK that is generated by Fitbit's backend and scoped to the owning account + device**. BlueBit cannot obtain this credential, so it is permanently limited to a **BOOTSTRAP** session — and under BOOTSTRAP the tracker refuses `bond/control`.

Concretely, three independent facts combine:

1. **The official resolver chain includes MobileData; BlueBit's does not.**
   - Official (at app init): `TlsKeyResolverRegistry.INSTANCE.register(new MobileDataTlsKeyResolver())` — `defpackage/nnw.java:269` (case 2), on top of the binding defaults `Hello → Bootstrap` (`com/fitbit/goldengate/bindings/dtls/TlsKeyResolverRegistry.java:11-19`).
   - ⇒ Official chain = **Hello → Bootstrap → MobileData**; BlueBit = **Hello → Bootstrap** (grep `MobileData|MD-` under `BlueBitApp/app/src` → 0 matches).

2. **The MobileData PSK is a server-generated, account+device-scoped secret.**
   - `MobileDataTlsKeyResolver.resolveKey` resolves `MD-*` identities only when the node key is a `BluetoothAddressNodeKey`, then calls `mobileDataKeyProvider.b(keyId)` (`dtls/MobileDataTlsKeyResolver.java:29-42`).
   - `mobileDataKeyProvider` (interface `plj`) is `qwi`, which returns the encoded key from an Android-keystore `SecretKey` (`defpackage/qwi.java:23-29`; wired at `defpackage/nnw.java:73`, `nqj.h = new qwi(pdk.b())`).
   - The key material is `DeviceAuthCredentials` (`com/fitbit/fbcomms/security/DeviceAuthCredentials.java`): `authSubKey` (hex → key bytes), `nonce` (→ key expiration), device type.
   - It is parsed from the backend response `{"btleClientAuthCredentials":{"authSubKey":…,"nonce":…}}` (`defpackage/qoo.java:35-47`) and fetched from the endpoint **`user/-/devices/tracker/generateBtleClientAuthCredentials`** keyed by serial number; absence throws `InvalidBLEAuthCredentials` (`defpackage/noi.java:154-167`, case 10). It is then stored encrypted as `trackerAuthCredentials.json` (`qoo.d`, `qoo.java:75-81`).
   - ⇒ The `authSubKey` is delivered **only** to the authenticated Fitbit app that owns the device on its account.

3. **`bond/control` is a pairing-time operation reached only through `createNewBond`.**
   - `GoldenGateCommandHandler.createNewBond(Context)` → `bondCommandsHandler.create(context, bluetoothAddress)` (`commands/GoldenGateCommandHandler.java:517-520`).
   - `BondCommandsHandler.create` → check bond state; if already bonded → complete; else `createBond`: read bond timeout, **remove any existing bond**, then `CoapBondControlResource.enable(address, timeout)` (CoAP `PUT bond/control`, body `BondControl.Control{operationTimeout}`), then `PeripheralBondCreator.create` → Android `createBond` (`bond/BondCommandsHandler.java:111-172`; `bond/CoapBondControlResource.java:51-56,119-139`; `bond/CreateBondTransactionProvider.java:21-25`).
   - Invoked from the pairing flow `pzv.x(context)` = connect/sync-setup (`qdy.c()` → `qez.c()`) → `createNewBond(context)` → set bond state (`defpackage/pzv.java:31-58`); also `ahso` and `pcx`.
   - `bond/control` uses the same `endpointMapper.map(address)` as `pair/display` — **no per-resource key selection and no explicit MD precondition inside the handler**. The precondition is external (the account credential + device ownership state).

## 3. Credential lifecycle (official app)

```
Fitbit backend (authenticated account, owns device)
        │  GET user/-/devices/tracker/generateBtleClientAuthCredentials?serialNumber=…
        │  → JSON { btleClientAuthCredentials: { authSubKey: <hex>, nonce: <exp> } }
        ▼
noi.java case 10                                         (defpackage/noi.java:154-167)
        │  qoo.b(deviceType, json) → DeviceAuthCredentials(type, authSubKey, nonce)
        │  qoo.d(serial, json, nuh) → encrypt → trackerAuthCredentials.json
        ▼
Android keystore (SecretKey)  ←  pdk.a(keyId)         (defpackage/qwi.java:23-29)
        ▲
        │  qwi.b(keyId)  [impl of plj.mobileDataKeyProvider]
MobileDataTlsKeyResolver.resolveKey(nodeKey, identity)   (dtls/MobileDataTlsKeyResolver.java:29-42)
        ▲
        │  DTLS server resolve on the phone (hub) for an `MD-<keyId>` PSK identity
Tracker (DTLS client) presents identity = MD-<keyId>-… → authSubKey
```

Because the `authSubKey` is issued by Fitbit's backend for the account that owns the tracker, a third-party app cannot fabricate or obtain it. The tracker also holds the matching key (it is the DTLS client that names the key id), so a wrong key fails the DTLS `Finished`.

## 4. `bond/control` invocation chain (official app)

```
pairing / onboarding UI
   └─ pzv.x(context)                                   (defpackage/pzv.java:44-58)
        ├─ qdy.c()  (= qez.c(): connect + sync-setup)  (defpackage/qdy.java:22-25, qez.java:26)
        ├─ a(context) = createNewBond(context)          (pzv.java:31-33)
        │     └─ GoldenGateCommandHandler.createNewBond (GoldenGateCommandHandler.java:517-520)
        │           └─ BondCommandsHandler.create        (BondCommandsHandler.java:111-129)
        │                 ├─ if already bonded → complete
        │                 └─ createBond:
        │                      ├─ read bleBondTimeout   (BondDeviceTimeoutProviderEntryPoint)
        │                      ├─ peripheralBondRemover  (remove existing OS bond)
        │                      ├─ CoapBondControlResource.enable(address, timeout)
        │                      │     └─ PUT bond/control  { operationTimeout }
        │                      └─ PeripheralBondCreator.create → Android createBond
        ├─ noi(this,16)  → on success, mark device record bonded
        └─ b(TrackerBondState.b.ordinal())  → state = BONDED_TO_CURRENT
```

`TrackerBondState` (`com/fitbit/fbcomms/bond/TrackerBondState.java:20-27`) = `{NOT_BONDED, BONDED_TO_CURRENT, BONDED_TO_OTHER, BONDED_NOT_SECURE}`. The app explicitly models an **already-owned ("bonded to other")** device.

## 5. Interpretation — C vs D

- The **mechanism** is: the tracker authorizes `bond/control` (and `/sync/config`) only on a session it trusts as the device owner. The official app's owner proof is the **MobileData PSK**, a server-generated, account+device credential.
- BlueBit is always BOOTSTRAP (it can never resolve `MD-*`), so `bond/control` → `4.01`. This is **A (missing/incorrect credential) + C (resource-specific authorization by session identity)**. Because the credential's provenance is a Fitbit-backend, account-scoped issue, it is *also* the "server-mediated provisioning" dependency identified by the Gadgetbridge work — but the operative cause is the **missing credential**, not an ordering bug.
- **Refinement / testable prediction:** since a *fresh* device must be provisioned under BOOTSTRAP in the first place, a BOOTSTRAP `bond/control` is presumably accepted for a **not-yet-owned** device (`TrackerBondState.NOT_BONDED`) and denied for an **already-owned** one (`BONDED_TO_OTHER`). BlueBit's target presents a MobileData identity (`MD-A376B03C-6AF89570`) ⇒ it is **already provisioned/owned** ⇒ `4.01` under BOOTSTRAP. This makes D (ownership/pairing state) a *contributing* condition rather than the primary mechanism.

Consistent with E1/E2: the same BOOTSTRAP session that allows `/pair/display` denies `/sync/config` with `4.01` — resource-level authorization by session trust.

---

## 6. Why the harness cannot settle it, and the single discriminating experiment

- The missing input is a **valid `authSubKey`** (server-issued) — which cannot be synthesised (a fabricated key fails the DTLS `Finished` against a provisioned device). A synthetic-identity harness can exercise BlueBit's code paths (§6 of the plan) but cannot obtain owner trust.
- Only a **live** run on a device that is **not yet owned** (factory-reset) with a plain BOOTSTRAP `bond/control`, or a run supplying a **synthetic** MD identity to observe the `Finished` failure, could further discriminate. Both need explicit approval; device reset is currently forbidden.
